# Fast Log-Domain Sinkhorn Optimal Transport with Warp-Level GPU Reductions

> Hao Xiao · arXiv 2026 · [arXiv](https://arxiv.org/abs/2605.00837) · 证据级 [R] · 课题 T29 高性能 OT 求解器与训练基础设施
> **一句话**：原生 CUDA log-domain Sinkhorn，warp shuffle 归约 + shared-memory tiling，n=8192 时比 POT 快 12×、比 PyTorch 快 5.9×，ε 低至 1e-4 稳定。

## 1. 问题

离散 OT 的精确求解（network simplex）复杂度为 $O(n^3\log n)$，Cuturi [2013] 引入熵正则化后，Sinkhorn 算法以每迭代近线性时间成为主流。但实际部署在 GPU 上仍有两个瓶颈：

**数值不稳定**：标准域 Sinkhorn 显式计算 Gibbs 核 $K_{ij}=\exp(-C_{ij}/\varepsilon)$。当 $\varepsilon$ 较小时，核元素跨越极端范围。原文给出具体例子：$C_{ij}\in[0,10]$、$\varepsilon=0.01$ 时，核元素跨度 $[e^{-1000},1]$，远超 IEEE 754 float32 的表示范围（约 $[10^{-38},10^{38}]$），导致灾难性下溢（Sec. 4.1）。Schmitzer [2019] 提出 log-domain 稳定化，但作者报告其未被 GPU 优化实现广泛采用（Sec. 1）。

**框架开销**：现有 GPU 实现依赖 PyTorch/JAX 或 KeOps/GeomLoss，引入 autograd 图、内存分配器、Python-to-GPU dispatch 的开销。对于只需要前向 OT 计算的应用（点云配准、颜色迁移、batch 距离计算），这些开销是不必要的（Sec. 1）。

## 2. 方法

核心思想：整个求解器在 log-domain 中运行，用两遍 LogSumExp 归约替代显式 Gibbs 核计算；GPU 并行化采用「一个 thread block 负责一行/一列」的映射，block 内用 warp-level shuffle 做归约，跨 warp 用 shared memory 通信。

**关键公式**：

稳定化 LogSumExp（Eq. 8）：
$$LSE(x_1,\dots,x_m)=\max_j x_j+\log\sum_{j=1}^{m}\exp(x_j-\max_j x_j)$$

log-domain Sinkhorn 对偶更新（Eqs. 9–10）：
$$\alpha_i=-\varepsilon\cdot LSE_j\left(\frac{\beta_j-C_{ij}}{\varepsilon}+\log\nu_j\right)$$
$$\beta_j=-\varepsilon\cdot LSE_i\left(\frac{\alpha_i-C_{ij}}{\varepsilon}+\log\mu_i\right)$$

收敛监控的行边际（Eq. 12）：
$$\log r_i=\log\mu_i+LSE_j\left(\frac{\alpha_i+\beta_j-C_{ij}}{\varepsilon}+\log\nu_j\right)$$

**算法流程**（Algorithm 1）：分配 GPU 上的 $C[n\times m]$、$\alpha[n]$、$\beta[m]$；预计算 $\log\mu$、$\log\nu$；迭代执行 `updateAlphaKernel`（每行一个 block）和 `updateBetaKernel`（每列一个 block）；每 $c=10$ 次迭代检查一次边际误差 $\sum_i|r_i-\mu_i|$，低于阈值 $\tau$ 即收敛；最后计算传输代价 $\langle C,\pi^\varepsilon\rangle$。

**GPU 归约层次**（Sec. 4.3）：warp 内用 `__shfl_down_sync` 做 butterfly 归约，$\log_2(32)=5$ 步完成，无 shared memory 访问、无同步屏障；跨 warp 时每个 warp 写一个结果到 shared memory（每 warp 一个槽位），第一个 warp 对 8 个值做最终归约。block size 取 $B=256$（8 个 warp）。该设计消除了 warp 内的 shared memory bank conflict，且 shared memory 槽位数固定为 32，与 block size 无关。

**内存布局**（Sec. 4.4）：cost 矩阵行主序存储。$\alpha$-update 中 block $i$ 顺序读第 $i$ 行，warp 内线程访问连续地址，实现 coalesced global load；$\beta$-update 按列访问，stride 为 $m$，依赖 L2 cache 缓解。$n=m=8192$ 时 cost 矩阵占 256 MB，对偶势约 64 KB。

## 3. 理论结果

无新理论结果。论文引用 Peyré & Cuturi [2019, Theorem 4.2] 的线性收敛定理（原文 Theorem 1）：Sinkhorn 迭代满足 $\|\alpha^{(k)}-\alpha^*\|_\infty\leq\lambda^k\|\alpha^{(0)}-\alpha^*\|_\infty$，其中 $\lambda=e^{-2R/\varepsilon}$，$R=\max_{i,j}C_{ij}-\min_{i,j}C_{ij}$ 为 cost 范围。附录 A.2 给出证明草图，指出收缩率由 Birkhoff 收缩系数 $\lambda=\tanh(R/4\varepsilon)^2\leq e^{-2R/\varepsilon}$ 决定，源自 Franklin & Lorenz [1989] 的正矩阵缩放经典结果。

## 4. 实验与数字

**硬件**：本文求解器在 NVIDIA RTX 3090（24 GB，82 SM，compute capability 8.6）；Python 基线（POT、GeomLoss、PyTorch Sinkhorn）在 NVIDIA Tesla T4（16 GB）上运行（Sec. 5）。注意：这是不同硬件之间的比较，作者在 Sec. 5.1 承认 RTX 3090 的 FP32 吞吐约为 T4 的 2.5×。

**主 benchmark**（Table 1，$\varepsilon=0.01$，均匀 1D 网格上的随机分布，平方欧氏 cost，10 次运行取平均，排除数据传输）：

| 方法 | n=256 | n=512 | n=1024 | n=2048 | n=4096 | n=8192 |
|---|---|---|---|---|---|---|
| POT (CPU) | 3.2 ms | 13.1 | 55.1 | 256.0 | 1097.2 | 4462.1 |
| GeomLoss (T4) | 37.1 | 24.1 | 23.5 | 80.0 | 304.8 | 1193.5 |
| PyTorch Sinkhorn (T4) | 10.5 | 10.3 | 36.6 | 135.9 | 533.5 | 2174.5 |
| Ours (RTX 3090) | 0.3 | 1.3 | 5.1 | 20.7 | 89.1 | 371.6 |
| Speedup vs. POT | 10.0× | 10.4× | 10.8× | 12.4× | 12.3× | 12.0× |
| Speedup vs. PyTorch | 32.4× | 8.2× | 7.2× | 6.6× | 6.0× | 5.9× |

**扩展性**（Sec. 5.2，Fig. 2）：$n=64$ 到 $n=16384$，$\varepsilon=0.01$。计算时间随 $n$ 二次增长，与稠密矩阵 $O(n^2)$ 每迭代成本一致。峰值 GPU 内存由 $n\times n$ cost 矩阵主导，$n=16384$ 时为 1024 MB。迭代次数约 180–200，近似不依赖 $n$（与 Theorem 1 一致：收敛率取决于 $\varepsilon$ 而非 $n$）。$n=16384$ 单卡 RTX 3090 耗时 1.54 s。

**消融**（Table 2，$n=m=2048$，$\varepsilon=0.01$，完整系统 14.8 ms）：

| 配置 | 时间 (ms) | 减速 |
|---|---|---|
| 完整系统 | 14.8 | 1.00× |
| 仅 shared memory（无 warp shuffle） | 28.5 | 1.93× |
| 标准域（无 log-LSE）† | 16.9 | 1.14× |
| Block size = 64 | 21.1 | 1.42× |
| Block size = 128 | 16.7 | 1.13× |
| Block size = 512 | 16.8 | 1.14× |
| 每次迭代检查收敛 | 24.8 | 1.68× |
| 检查间隔 = 5 | 16.8 | 1.14× |
| 检查间隔 = 10 | 15.2 | 1.03× |

† 标准域求解器在 $\varepsilon<0.005$ 时产生 NaN；表中时间仅在 $\varepsilon=0.01$ 下报告。

**数值稳定性**（Sec. 5.4，Fig. 4）：$\varepsilon$ 从 1.0 扫到 $10^{-4}$，$n=512$。标准域求解器在 $\varepsilon<0.005$ 时因 Gibbs 核 $\exp(-C_{ij}/\varepsilon)$ 溢出产生 NaN；log-domain 求解器在所有测试值下稳定收敛到 $\varepsilon=10^{-4}$。两种方法在 $\varepsilon\geq0.01$ 时产生可比的传输代价。

**收敛分析**（Fig. 5）：所有配置在少量迭代内收敛到机器精度边际误差；$\varepsilon$ 越小所需迭代越多。Table 3 给出扩展数据：$n=8192$、$\varepsilon=0.001$ 时 294 次迭代、714.88 ms；$\varepsilon=0.1$ 时 30 次迭代、176.51 ms。

**应用**（Sec. 5.6）：图像颜色迁移（$N=512$ 像素采样，$\varepsilon=0.01$，barycentric mapping）；3D 点云匹配（$n=200$，目标为源点云的旋转平移 + 高斯噪声，OT plan 恢复正确对应）。

## 5. 在 OT×扩散地图中的位置

本文属于「kernel 级 IO 工程」这一支线，与 FlashSinkhorn（ICML 2026 Oral）同代但走不同技术路线：FlashSinkhorn 把稳定化 Sinkhorn 更新识别为 attention 归一化的同构形式，搬 FlashAttention 的 tiling/online-softmax 做一次 pass 流式归约，显存从 $O(n^2)$ 降到 $O(nd)$；本文则保留稠密 cost 矩阵（$O(n^2)$ 显存），在「cost 矩阵能放进 GPU 显存」的范围内（$n,m\leq16384$）用原生 CUDA 消除框架开销。两者是竞争关系，但适用规模不同：本文明确将目标定位为「dense, moderate-sized ($n,m\leq16384$) OT problems where the full cost matrix fits in GPU memory」（Sec. 2），而 FlashSinkhorn 面向更大规模、显存受限的场景。

在扩散/流匹配训练管线中，batch 内 OT 配对的 batch size 通常在 $10^2$–$10^4$ 量级，恰好落在本文的目标范围内。本文求解器不支持自动微分（Sec. 6 明确列出），因此不能直接用于需要梯度的训练场景；但前向 OT 计算（如配对质量评估、颜色迁移、点云配准）可以直接受益。与 Immiscible Diffusion 的量化指派（毫秒级）相比，本文在 $n=256$ 时 0.3 ms、$n=512$ 时 1.3 ms（Table 1），量级相当但提供的是精确 Sinkhorn 解而非近似指派。

## 6. 局限与批评

**作者承认的**（Sec. 6 Limitations）：
1. 仅支持 float32 单精度，对需要非常高精度的场景可能不足。
2. 稠密 cost 矩阵存储限制可扩展性至约 $n=m=16384$（16 GB GPU）。
3. 不支持自动微分，无法直接用于基于梯度的学习管线。

**读出来的**：
1. **硬件不对等的 benchmark**：本文求解器在 RTX 3090 上运行，而 GPU 基线（GeomLoss、PyTorch）在 Tesla T4 上运行。作者在 Sec. 5.1 承认 RTX 3090 的 FP32 吞吐约为 T4 的 2.5×，并声称「即使考虑这一差异仍保留显著优势」，但未给出归一化后的数字。这意味着 5.9× 的 PyTorch speedup 中约 2.5× 来自硬件差异，实际算法/工程优势约为 2.4×。
2. **问题设置过于简单**：主 benchmark 使用「均匀 1D 网格上的随机分布 + 平方欧氏 cost」（Sec. 5.1），这是 Sinkhorn 最友好的设置之一。cost 矩阵的规律性可能使 L2 cache 行为异常有利，不能代表一般 cost 矩阵（如高维点云、cosine 距离）下的性能。
3. **收敛判据的边际误差计算本身需要额外 pass**：Eq. 12 的 $r_i$ 计算复用 LSE kernel 结构，但每 $c=10$ 次迭代做一次完整行边际归约，其成本在 Table 2 中体现为「检查间隔」消融的 1.68× 差异。对于 $\varepsilon$ 很小、迭代次数很多的场景，这个开销会被放大。

## 7. 对我们的启发

1. **前向 OT 配对的低成本选项**：本文在 $n=256$ 时 0.3 ms、$n=512$ 时 1.3 ms（Table 1），且无 Python 开销、无 autograd 图。对于扩散训练中只需要前向配对质量评估（不需要梯度流经 OT plan）的场景，这是一个比 POT/GeomLoss 更轻量的选择。但需注意硬件差异：这些数字在 RTX 3090 上测得，实际部署需在自己的 GPU 上重新校准。
2. **log-domain 稳定化是低 ε 的硬前提**：Fig. 4 显示标准域在 $\varepsilon<0.005$ 时 NaN，log-domain 稳定到 $10^{-4}$。如果我们的 OT-aware 采样调度或保耦合蒸馏需要小 ε 的精确 OT 解，log-domain 是必须的，且本文的两遍 LSE 结构可以直接复用。
3. **warp-level 归约的工程价值可迁移**：1.93× 的 warp shuffle 加速（Table 2）是纯 CUDA 工程优化，与 OT 算法本身无关。如果我们要写自己的 CUDA/Triton kernel（如 MPNA 的 batch 级噪声指派、或 OT 配对的 GPU 实现），「warp 内 shuffle 归约 + 跨 warp shared memory」的层次设计是可直接借鉴的模式。
